# ADR-0036 `concurrentRate`：语法、单位与「速率门 + 并发门」的合成

- **状态：** Accepted（2026-10-13 架构师裁决；`PLAN.md` §3.5 的 M1-b0 规格前置）
- **日期：** 2026-10-13
- **关联：** ADR-0027（事实级唯一归属）、C-SRC-9（可并发调用）、C-NET-2（有限重试）、
  C-NET-6（缓存 TTL）、`docs/dev/book-source.md` §8（数值与语义的唯一出处）、`PLAN.md` §3.5 / §3.7

## 背景

3.8 已在请求层落了**并发数**门（同一书源最多 3 个在飞请求，`RequestLimiter`，见 §8）。
M1 的 `concurrentRate` 是**速率**门：两者量纲不同（同时在飞的数量 vs 单位时间内的次数），
共存方式必须裁决，否则开发组只能猜——而猜错会让「书源声明了限速却仍被站点封」这类问题
在真实语料里才暴露。

上游取证（fork `HapeLee/legado-with-MD3@master`，本地 clone `F:/Projetcs/legado-fork`）：

| 事实 | 出处 |
|---|---|
| `n/m` 解析为 `accessLimit = n`、`interval = m`；无 `/` 时 `accessLimit = 1`、`interval = x`；`n <= 0` 或 `m <= 0` → 抛 `NumberFormatException` 被吞（保留上一条记录） | `app/src/main/java/io/legado/app/help/ConcurrentRateLimiter.kt:17-46` |
| 单位为**毫秒**，原文注释：`//并发控制为 次数/毫秒 , 非并发实际为1/毫秒` | 同上 `:86` |
| `concurrentRate` 为空或 `"0"` → 不限速；首次解析失败用 `toIntOrNull() ?: 1` / `?: 0` 兜底 | 同上 `:52-70` |
| 超限**抛 `ConcurrentException` 并在 `getConcurrentRecord()` 里 `delay(waitTime)` 重试** → 语义是**排队等待**，不是失败 | 同上 `:88-108` |
| 应用点覆盖所有出网请求：OkHttp 拦截器 / `AnalyzeUrl` / 脚本的 `http.*` | `help/http/HttpHelper.kt:164`、`model/analyzeRule/AnalyzeUrl.kt:121`、`help/JsExtensions.kt:512/538/569` |
| 声明与书源对象绑定，赋值时重建限速记录 | `data/entities/BaseSource.kt:323-326` |

## 决策

1. **语法与单位照抄上游，唯一出处是 `book-source.md` §8**（本 ADR 不复述表格）：
   `n/m` = 每 `m` **毫秒**内最多 `n` 次；单个整数 `x` = 每 `x` 毫秒 1 次；`"0"` 或空 = 不限速。
2. **非法声明显式降级，不静默**：非整数、`n <= 0`、`m <= 0`、`x <= 0` → **忽略该书源声明**
   + 一条 warning（含书源 ID、字段名与原文摘要，C-ERR-8 / C-SEC-4），行为回退到默认并发 3。
   *（与上游的差异：上游把畸形值吞成 `1` / `0` 或保留旧记录，既不记录也不可观测。）*
3. **两把门同时生效，互不替代**：请求必须**同时**通过「速率门」（`n/m` 滑窗）与「并发门」（默认 3）。
   合成顺序固定为 **先取速率许可，再占并发槽位**——反过来会让等待中的请求白占并发槽位，
   3 个槽位被等待者占满即整源停摆。
4. **超限排队，不报 busy**（延续 §8 的既有语义；C-SRC-9 要求 `RuleEngine` 可并发调用）。
5. **唯一实现点仍是 `DioHttpClient` 的 `RequestLimiter`**：速率状态按**书源**键控（与并发槽位同键，
   无书源上下文时同 §8 回退到 URL 主机）；**不为速率新增第二实现点**，也不把它提到
   `HttpPolicy` / `JsBridge` 契约里（ADR-0030 §决策 2 的口径不变）。
   `http.*`（脚本）与页面抓取共用同一份预算，故 `concurrentRate` **自动覆盖两者**（§8 已登记）。
6. **默认不限速**：只有书源声明了 `concurrentRate` 才启用速率门；`HttpPolicy` **不新增**默认速率
   字段（不改变既有行为，也不扩大契约）。
7. **模型读取点是 `BookSource.concurrentRate`**（M1-b2 建模）。运行时更新（编辑书源后重建限速记录）
   归「导入 / 导出 + 书源编辑」，未排期；M1 只从模型读。
8. **重开触发条件（必须新 ADR，不得就地改）**：真实语料若证明作者把 `n/m` 当成「n 次 / m **秒**」
   （毫秒口径下 `30/60` 几乎是无限速），以**真实语料证据 + 新 ADR** 裁决单位。
   M1-b2 的验收因此**包含**一项统计：在入库语料上统计 `concurrentRate` 的取值分布，
   并给出「作者意图单位」的判断记录（写进 PR 与 `tool/spot_check/README.md` 的回归记录）。

## 后果

- `RequestLimiter` 从「只有信号量」变成「速率门 → 并发门」两段；并发语义（FIFO、异常也释放槽位）
  不变，速率门不占用并发槽位。
- §8 的 `concurrentRate 覆盖` 行从「按书源声明解析」改为指向本 ADR 的合成规则（数值仍在 §8）。
- 非法声明从「静默无效果」变成「warning + 回退默认」——属于 C-SRC-4 的同一精神：无效要显式记录。
- `PLAN.md` §3.5 的 M1-b2 验收增加「语料统计 + 单位判断记录」与「速率/并发两门各自的单测」。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| 只保留更严格的一把门（取 min） | 两把门量纲不同（在飞个数 vs 次数/时间），「取 min」没有定义；且 `n/m` 很宽松时会丢掉默认并发 3 的保护 |
| 用 `n` 覆盖并发上限（把并发数也改成 `n`） | 上游两把门各自独立（拦截器与 `AnalyzeUrl` 各持 limiter），合并会改动已落地的 3.8 语义 |
| 单位改成「秒」（更符合直觉） | 与上游代码不符；要改必须先有真实语料证据（决策 8） |
| 在 `HttpPolicy` 加全局默认速率 | 没有需求；「默认不限速」才是不改变既有行为的选择 |
| 把速率门放在 JS 桥（只限 `http.*`） | 页面抓取才是主要流量，只限脚本等于没限；且会新增第二个实现点 |
