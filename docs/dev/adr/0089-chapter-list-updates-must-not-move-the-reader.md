# ADR-0089 目录更新不许挪动读者：刷新不换屏、位置来自内存、下标按 URL 搬

- **状态：** Accepted（2026-10-29，用户报障：书更了新章节时阅读页闪屏，且滚动进度因页面变长而错位）
- **日期：** 2026-10-29
- **关联：** ADR-0044 §决策 2/4（会话与进度、按比例估算偏移）、ADR-0066 §决策 7（偏移落地）、
  ADR-0087 §决策 1/2（单一页表、零跳）、ADR-0088（跨章上限与预取窗口，正文会陆续到达）;
  `docs/dev/constraints.md` C-STATE-6、C-ERR-4；上游 `ReadBook.kt:1798 upToc()` /
  `ReadBook.kt:1529`

## 背景

书在别处（书架、详情页、后台）更新出更多章节后，阅读页会出现两个症状：

1. **闪屏**：整块正文被一个转圈替掉，再整块换回来；
2. **错位**：转圈之后落点不对，「页面变长」以后滚动进度对不上读者原来读的那一段字。

根因是两处「刷新等于重建」：

- `readerChaptersProvider` 是**被 watch 的依赖**，目录刷新时它会重新发出（先 `AsyncLoading`，再带
  新列表）。页面用 `switch (chapters) { AsyncData(:final value) => …, _ => 转圈 }` 分支，于是刷新
  期间整块正文换成转圈——**闪屏**，而且正文流程（`ReaderScrollFlow` / `ReaderPagedFlow`）连同它的
  `State` 一起被销毁，滚动位置没了。
- `ReaderSession.build` 也 `ref.watch` 目录，于是同一次刷新会让**会话重建**；重建走的是
  「从磁盘读存档」那条路（`readerProgressStore.read`），把**内存里的当前屏**换成了上一次落盘的
  位置。落盘只在换章与停手时发生，读数与当前屏本来就差一截。
- 另外目录变长会让下标含义变：源在**前面**插入章节时，`chapterIndex` 指向的已经不是读者读的那一章。

上游不这么做（`ReadBook.kt:1798 upToc()`）：拉目录发生在 IO 线程，只有 `cList.size > chapterSize`
才整表替换 **数据库**，然后 `saveRead()`、`publishSnapshot()`、必要时 `loadContent(durChapterIndex + 1)`
——`durChapterIndex` / `durChapterPos` / 视口一个都不动。它的阅读状态是「指向目录的下标 + 章内偏移」，
而目录只会在末尾变长，所以位置天然不用换算。

## 决策

### 决策 1 刷新期间继续画**上一次的值**，只有「从来没有过」才画转圈

`AsyncValue` 在重新计算时仍然带着上一次的值（`AsyncLoading.hasValue` / `AsyncError.hasValue`）。页面
因此按 **`.value`** 分支，而不是按 `AsyncValue` 的形状分支：

- 有值（哪怕是刷新中、哪怕这次刷新失败了）→ 照常画正文；
- 没有值且出错 → 失败态 + 重试；
- 没有值也没出错 → 转圈（首次加载）。

章节列表与会话**都**按这条规矩（`_bodyOf` / `_sessionBody`）。这条同时解决了「流程 State 被销毁」
——因为正文那一层根本没有被替换。

### 决策 2 会话重建时位置来自**内存**，不从磁盘重读

`ReaderSession` 记住当前 `(chapterIndex, charOffset)`（`_position`，与 `state` 一起维护），`build`
被重建时用它，**不再** `readerProgressStore.read`：

- 磁盘只在「首次打开这个会话」时才是权威；重建是同一段阅读中的事件，内存里的才是真的。
- 落盘失败、或别处写入了更旧的进度时，磁盘值会把读者拽回去——上游也不会因为目录更新重读进度。

### 决策 3 下标按**章节 URL** 搬，不按下标搬

重建时用「重建前的目录 + 旧下标」取出当前章的 URL，在新目录里找它的新下标；找到就搬过去，字符
偏移一个都不动，找不到（源真的删章/重排到对不上）才退回原下标——与首次恢复「找不到就回第一章」
不同：**读到一半不能把读者踢回书首**。

### 决策 4 目录变长要重排预取队列

ADR-0088 的预取队列只在「锚点章变化」时重排，目录变长时锚点没变，新章节因此永远进不了队列。
队列的重建条件加上**章数**：`_prefetchAnchor` 与 `_prefetchCount` 任一变化就重排。

## 后果

- `reader_page.dart`：`_bodyOf` / `_sessionBody` 改为按 `.value` 分支；`_queuePrefetches` 多一个
  `_prefetchCount`。
- `reader_session_notifier.dart`：新增 `_position`、`_known`（上一次的目录）与 `_urlAt`；`build` 的
  两条路径（首次 / 重建）分开，重建按 URL 搬下标。
- 新增测试：会话「目录末尾变长 → 保留内存位置」「前面插入 → 下标搬对」；页面「目录刷新时没有
  转圈、会话与滚动位置都不动」。
- 未变：进度仍只在换章与停手时落盘；目录仍是「整表读出来」（不做上游那种「只接受更长」的联合，
  因为本仓的目录来自一次 `FetchToc`，没有本地表要维护）。

## 修订

- **2026-10-29（用户报障「还是乱跳、跳到第一章」）**：§决策 2 漏了一半——`_position` 只在
  `selectChapter` / `updateOffset` 里赋值，**`build` 自己算出来的那个位置从来没记住**。于是：
  读者打开一本书、一屏都没滑（流程第一次上报的偏移就是 0，`updateOffset` 当作没变化直接返回），
  `_position` 一直是 null；这时目录刷新 → 重建又走「首次打开」那条路 → 重读磁盘 → 磁盘里没有这本书
  （或写着别的章）就落到**第一章**。真机上看到的就是「进度乱跳、跳到第一章」，而且每刷新一次跳一次。
  修法：`build` 的每条成功返回都经 `_remember` 记下位置（失败那条**不记**——目录没读到不算位置，
  否则下次读到了会带着错的位置走）。
  测试：`build_whenTheRestoredPositionWasNeverScrolled_keepsItAcrossARefresh`——把 `_remember` 改成
  不赋值，它就红（2 → 0）。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| 目录刷新时干脆不刷新（读一次就缓存到页面销毁） | 书更了章节读者看不到，反而要退出重进；上游也是会自动更新的 |
| 刷新期间保留转圈但保住滚动位置（记住 offset 再恢复） | 转圈本身就是要修的症状；而且流程重建后页码/页高都可能变，恢复必然有误差 |
| 会话继续 `ref.watch` 目录并重读磁盘，只在外面兜住闪屏 | 落点是「上一次落盘」而不是「当前屏」，错位还在；上游也不这么做 |
| 目录更新时把 `chapterIndex` 按下标平移（差几章挪几章） | 只在「末尾追加」时成立；源在前面插入或删章时会把读者挪到别的章 |
