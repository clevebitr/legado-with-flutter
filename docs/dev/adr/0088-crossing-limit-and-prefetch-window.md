# ADR-0088 跨章上限与 ±15 章预取：阅读位置不许跑到已加载内容前面

- **状态：** Accepted（2026-10-29，用户裁决两项：①限制一次滑动跨过多章加载 ②两侧各提前缓存 15 章）
- **日期：** 2026-10-29
- **关联：** ADR-0085 §决策 3（预取固定相邻各一章，本 ADR 推翻其「固定 ±1、不做设置面」）、
  ADR-0087 §决策 1/2（单一页表、零跳）、`docs/dev/constraints.md` C-NET-2/6、C-PERF-1/2、
  `docs/dev/roadmap.md` §3.7（「预加载章数可配」登记项，本 ADR 部分结清）；上游
  `ReadBook.kt:1919-1924` 的 `preDownloadNum` / `preDownloadNumPrev`

## 背景

ADR-0085 §决策 3 把预取固定成「当前章 ±1」，理由是设置面成本高、先对齐行为。那个决定在
**慢网 + 快滑**下暴露了两个问题（用户报障）：

1. **一次下滑能跨过好几章**。窗口是 `[windowFirst, anchor + 1]`，锚点每前进一章，页表就往
   下补一章；补进来的那一章若正文还没到手，它是一页「正在加载」。快速滑动时锚点连续前进，
   于是连续补进来好几页占位——读者一次性跨过好几章空白。
2. **那几章会同时被拉起来**。占位页一被渲染就由流程的 `_requestMissingBodies` 逐个请求，
   于是同一个书源上并发打出去好几个正文请求。书源自己的限速（`concurrentRate`）与并发预算
   （ADR-0036）会排队，但排队的形态不受阅读器控制：既不是「最近优先」，也没有上限。

根子是同一条：**阅读位置可以跑到「已经拿到的正文」前面**。上游不让它跑：预取由
`preDownloadNum` 门控，页表里邻章没排完时给的是**同 id 占位页**，而滚动手势的跨界由宿主在
同一帧里裁决（`ReaderScrollPolicy.apply` 的 `hasNext`）。

## 决策

### 决策 1 阅读位置最多跨进**一章未加载**的章，跨不过第二章

页表的右边界不再是恒定的 `anchor + 1`，而是由「锚点章的正文在不在手上」决定：

| 锚点章正文 | 页表右边界 | 读者能做什么 |
|---|---|---|
| 还没到 | `anchor`（只有它自己那一页） | 停在加载页上，滑不动了 |
| 到手了 | `anchor + 1`（已加载 = 真实页；未加载 = 一页加载页） | 可以跨进下一章 |

跨进下一章后它自己就成了锚点章；它的正文没到手，右边界因此收回 `anchor` —— 快速滑动到这里就
停住，等正文到达再往下接。**结果：任何时刻，读者身前最多只有一章是「没有正文」的。**

这一条同时把「一次滑动跨过多章」和「多章同时被拉起」一起关掉：能被跨过去的章一律是**已经抓好**的
章，跨章本身不再产生新请求。

### 决策 2 预取窗口 = 两侧各 15 章，队列化、最近优先、同一时刻只发一个

- 半径固定 `_prefetchRadius = 15`（用户裁决的数值；设置面仍未做，登记在 `roadmap.md` §3.7）。
- 预取走一条**队列**：锚点章变化时重排，顺序是「后 1、前 1、后 2、前 2、…」，已经到手 / 已失败 /
  已在飞行中的章跳过。
- **同一时刻只有一个请求在飞**，它完成后泵下一个。理由：书的正文请求要走书源自己的限速与并发
  预算，阅读器不该一次性甩 30 个进去；串行还让「最近优先」真的有意义（先到的永远是读者下一章）。
- 队列随窗口移动重排，离开 ±15 的待取项直接丢弃；换源换 generation 时整队作废。

### 决策 3 保留范围分两层：正文原文留 ±15，排版与测量只留渲染窗口

- 正文原文（`_prefetchedBodies`，按 URL）留 `anchor ± 15`：这是提前缓存的**内容**，滑回来不必再问
  一次（命中也只是本地缓存，但省一次适配器往返）。
- 排版后的正文（`_laidOut`，按章下标）与页高测量（`_measures`）只留**渲染窗口**：排版随字号/段距
  变化而失效，留着几十章的量法没有意义（C-PERF-1），要的时候从原文重算一次即可。

### 实现注记（2026-10-29，落地时定死的三处）

1. **接力加载不得清掉「已失败」标记**。ADR-0085 §决策 5 让「占位页在等」和「读者点重新加载」
   走同一个回调，于是接力请求会把失败标记清掉 → 屏幕和预取队列轮流为同一章发请求，一帧一个。
   现在回调带 `explicit`（只有「重新加载」按钮传 `true`）：接力只做「没失败、没在飞、不在队列」三条
   里剩下的那件事。
2. **锚点章不走队列**。它由页面自己 watch 的 provider 负责；接力请求碰到它直接返回（**不要** `read`
   那个 provider：`ref.read` 会把一个没人监听的 provider 现造出来，等于凭空多发一个请求）。
3. **串行队列要自己 `scheduleFrame`**。`addPostFrameCallback` 不排帧：链条的第一跳之后若没有别的
   东西要求重绘（读者静止时就是这样），预取会停在那里。`_afterFrame` 里补一次 `scheduleFrame`。

## 后果

- `reader_page.dart`：页表右边界由「锚点章是否就绪」决定；`_schedulePrefetch(chapter)` 换成
  `_queuePrefetches(anchor)` + `_pumpPrefetch()`（一个在飞）＋ `_retainBodies(anchor, window)`；
  `_needChapter`（占位页上的「重新加载」）把该章插到队首。
- ARB / 设置 / 数据层不动；预取的请求上下文仍是完整章节上下文（ADR-0085 §决策 3 那一条保留）。
- 冷启动时打开一本书会在后台串行抓最多 30 章。正文走 5.2 缓存，重复打开不再发请求；失败按
  `_prefetchFailed` 记下，不重试、不阻塞阅读。
- 读者行为上的可见变化：第一次向下滑到头会**停在加载页**上等一会儿（而不是继续滑过空白）；
  正文到手后自动可以继续。这是用户裁决要的「限制」。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| 只把预取加到 ±15，不加跨章上限 | 慢网下仍然能一次滑过好几章空白：预取没到就是没到，上限管的是「没到的时候不许跑」 |
| 允许跨多章，但把并发请求限成 1 | 读者眼前仍是空白页；而且「跨过多少章」本身就不该由一次手势的速度决定 |
| 把 ±15 做成设置项（滑块 + 仓储 + ARB） | 用户要的是「提前缓存 15 章」，不是设置面；设置面仍登记在 §3.7，触发 = 有人要改这个数 |
| 预取并发开到 3~5（快一点） | 与书源自身的并发预算抢额度，且「最近优先」失效；串行 15 章在真机上是十几秒的后台工作，读者感觉不到 |
| 预取不落地，只在内存里留最近 N 章 | 5.2 正文缓存本来就落盘（TTL 半天），再压一层只会让「滑回来」重新走适配器 |
