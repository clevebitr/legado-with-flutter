# ADR-0030 JS 引擎容量与排队：单常驻 worker + 单复用运行时 + FIFO，容量**不进** `JsBridge` 契约

- **状态：** Accepted（2026-10-11 架构师裁决；用户授权「你给决策就可」）
- **日期：** 2026-10-11
- **关联：** ADR-0015、ADR-0029、C-SRC-2、C-SRC-3、C-SRC-9、C-ERR-1、C-PERF-4、
  `docs/dev/book-source.md` §6/§7/§8、`docs/dev/testing.md` §4、`PLAN.md` §3.3/§3.7/§3.8、
  `tool/spike/README.md` §4

## 背景

ADR-0029 §后果 留了一条前置：**3.8（同一书源并发上限）与 JS 容量直接耦合，worker 的引擎数与
排队策略必须先定，否则 `JsBridge` 契约会随并发策略返工。** 开发组给出三个候选：

| 候选 | 主张 | 主张的代价 |
|---|---|---|
| 1 | 单个常驻 worker，1 个复用运行时，请求 FIFO 串行；契约不带容量参数 | 吞吐上限 = 串行 |
| 2 | `JsEnginePool` 保 N 个运行时，租借 + 排队；契约暴露 `maxEngines` 等容量参数 | 契约把容量写死，3.8 落地时可能再改 |
| 3 | 按 `sourceId` 各持常驻 worker | 桥接要管书源生命周期与上限，DI / 清理变重 |

取证（2026-10-11，`flutter_qjs_next 1.5.2` 本地 pub cache + `tool/spike/` 实测）：

1. **中断预算是「每次求值」重新起算的**：spike 探针 07 的 runaway 在 2012ms 被准确中断，且
   **同一个运行时随后 `1 + 1` 仍返回 2**（`tool/spike/README.md` §1、ADR-0015 实测表）。
   若预算是一次性消耗，第二次求值不可能成功。⇒ 单运行时也能满足 §6 的「单次 JS 墙钟超时」
   （该结论为**实测推论**，原生侧实现未逐行核实；若未来引擎行为变化，以探针重跑为准）。
2. **池化的内存预算是乘法**：官方 production checklist 与 engine-pool 文档写明
   「粗算上限 ≈ `maxSize × memoryLimit`」，且**池不强制总 RSS 预算**；而 `memoryLimit` 只是
   **每个运行时**的 QuickJS 堆上限（数值出处为 `book-source.md` §6，本 ADR 不复述）。
   ⇒ N 个运行时 = N × 该上限。
3. **多租户隔离的代价官方已量化**：`resetMode: none`（默认）「不是 multi-tenant safe」；
   `soft`（清 globals / channels / timers，代价 = 新 context）才是多租户默认，且**要求每次租借
   重新注册桥接**；`hard` 在 soak 中吞吐 **-19%** 且 **RSS 并不更低**。
4. **官方 checklist 的结论**：热路径用「**一个运行时或一个池**」，禁止每次调用创建；
   `memoryLimit` 不能当作进程 RSS。
5. **仓内对 `@js:` 是零语料**（ADR-0029 背景 4：`test/fixtures/book_sources/*.json` 中出现 0 次），
   所以「吞吐更好」目前**没有任何测量依据**。

## 决策

1. **3.3 采用候选 1**：一个常驻 worker isolate + **一个复用运行时**（spike §4.4「必须复用」）+
   **FIFO 串行队列**。
2. **容量不进 `JsBridge` 契约。** 契约只有异步求值方法（形状归 ADR-0029 决策 1/2），不带
   `maxEngines` / 队列深度 / 并发数参数；**并发预算是请求层的策略**，由 `PLAN.md` 3.8 实现
   （`book-source.md` §8 的「同一书源默认并发上限」）。这样 3.8 落地时只动请求层，契约不变
   —— 这正是 ADR-0029 §后果 要求前置裁决的原因。
3. **排队与超时语义**（数值一律以 `book-source.md` §6 为准，本 ADR 不复述数字）：
   - 多次并发调用按 FIFO 排队，**不得**以「busy」失败（C-SRC-9 要求可并发调用）；
   - 配额从**该请求开始执行**时计，不从入队时计；排队时长由调用方自己的请求级超时约束；
   - runaway → 引擎中断，该请求失败为 `ParseFailureKind.parseFailed`（`rulePath` 标注
     `js:timeout`，§7），**运行时继续可用**（背景 1）；
   - 中断无效或 worker 崩溃 → `Isolate.kill(priority: immediate)` 兜底（ADR-0015 §决策 3），
     worker 按需重建，在途请求失败、队列继续；
   - 单条规则的 JS 调用次数上限（§6）由 worker 按 **job** 计数，超限使该 job 失败。
4. **跨书源状态：`globalThis` 在 3.3 由所有书源共用 —— 登记为与上游的已知偏离，不假装无事。**
   上游是「每书源一个引擎」，本仓 3.3 不是。理由是背景 2/3/5：`none` 是官方「同租户热复用」
   形态，而 `soft` 要求每次租借重注册桥接、在交错请求下等于每次求值重建上下文；在零语料、
   零测量下不值得付。缓解措施：
   - `java.put(key, value)` / `java.get(key)`（M1，矩阵 #16/#17）的变量存 **Dart 侧、且与运行时
     同 isolate（worker 内）**，按 `sourceId` 键控 —— 同 isolate 才能让这两个绑定保持同步取值
     （`book-source.md` §6 的形态规定），同时不落 `globalThis`；
   - 规则向 `globalThis` 写入属 `book-source.md` §6 白名单**之外**的行为，不在支持面；
   - 测试必须钉住「按源状态来自 Dart 侧」，防止将来把泄漏当特性。
5. **重开触发（满足任一即必须重新裁决，不得就地放宽）：**
   (a) M1 的 `java.put` / `java.get` 落地 —— 按源变量语义开始 load-bearing；
   (b) 3.7 真实语料出现「定义全局函数/变量并跨规则复用」的规则；
   (c) 3.8 落地后**有实测数字**表明串行队列是吞吐瓶颈。
   届时首选**候选 2（引擎池）+ 按源 `soft` reset**：它是**实现变更，契约不变**。
   **候选 3（每书源 worker）必须另立 ADR** —— 它把书源生命周期、清理与上限搬进桥接层，
   牵动 DI 与 `core/` 边界，不属于实现细节。
6. **生命周期**：worker 懒创建（首个 `@js:` 规则时），随 Provider 作用域 `ref.onDispose` 释放；
   禁止每次求值创建运行时（背景 4）。

## 后果

- **ADR-0029 §后果的前置就此闭环**：`JsBridge` 契约的**容量**维度已定（异步求值 + 无容量参数），
  `PLAN.md` §3.7 的「3.8 先于桥接契约冻结」条目改为指向本 ADR。
  > **注记（2026-10-11，架构师）：** 「容量前置已闭环」**不**等于契约现在可以冻结。`PLAN.md` §3.3
  > 的**冻结前置**仍要求 G2b spot-check 与 3.5 / 3.8 先行：3.5 的 `nextTocUrl` / `nextContentUrl`
  > 允许 JS 返回 URL **数组**（`book-source.md` §4.1），「返回单值 vs 列表」这一维度必须先被真实
  > 字段行使。本 ADR 只解除容量阻塞，不改变 `PLAN.md` §3.4 的执行顺序。
- `PLAN.md` §3.3 的验收增加「并发调用按 FIFO 排队且不抛 busy」「超时后运行时仍可用」两条；
  §3.8 只动请求层（同一书源并发上限、章节正文串行/有限并发）。
- 内存预算：单运行时 ⇒ 一份 QuickJS 堆上限（§6），不存在池化的 `maxSize × limit` 问题；
  代价是吞吐上限，由背景 5 的触发条件决定是否重开。
- 已知偏离（决策 4）必须以测试固定：**按源变量来自 Dart**；跨源 `globalThis` 共享登记在案。
- 本 ADR 不含 `flutter_qjs_next` 的任何配额数值，避免与 `book-source.md` §6 形成第二份定义
  （ADR-0013 §3）。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| **候选 2**：`JsEnginePool` + 契约暴露 `maxEngines` | ① 把容量写进契约，3.8 落地时反而要改契约（正是本 ADR 要防止的返工）；② 收益是假定的吞吐，仓内零语料、零测量（背景 5）；③ 内存按 `maxSize × memoryLimit` 放大（背景 2），而官方明说池不管理总 RSS；④ 隔离收益也拿不到：多租户安全需要 `soft` reset，而 reset 要每次租借重注册桥接（背景 3），与「交错请求热复用」目标相抵 |
| **候选 3**：每书源一个常驻 worker | ① 桥接层被迫持有书源生命周期、上限与清理策略，与 `domain/` 只依赖注入抽象（ADR-0029 决策 2）冲突；② 手机端 worker 数随书源数增长，无上限依据；③ 同样零测量依据。不否决其**将来**的可能，但要求另立 ADR（决策 5） |
| 每次求值新建运行时 | 直接违反 spike §4.4「必须复用运行时」与官方 checklist（背景 4），且放大创建成本 |
| 用 `hard` reset 换「干净」 | 官方实测吞吐 -19% 且 RSS 不降（背景 3），是纯粹的成本 |
